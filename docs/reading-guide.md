# 阅读路线：从接口到完整产品

本文提供各开源项目的源码入口与通用练习。先按 [通用学习路线](roadmap.md) 选择相关章节，再用模拟传感器和通信终端练习接口、状态所有权、平台适配与任务通信。升级内容见 [通用固件升级学习路线](firmware-upgrade-study.md)。

## 1. littlefs：先理解可替换的依赖

阅读顺序：

1. `sources/littlefs/lfs.h` 的 `struct lfs_config`。
2. 找到 `context` 和 `read`、`prog`、`erase`、`sync` 回调的定义。
3. 在 `lfs.c` 中追踪回调的调用，以及错误如何传回调用者。
4. 观察实例状态、配置与外部设备的关系。

先关注接口边界。核心文件系统通过约定调用存储能力，实际设备操作由外部提供。函数指针提供替换点，`context` 使实现可以持有自己的设备状态。

练习：设计一个 C 串口发送接口，分别接入真实 UART 与内存记录器。

```c
typedef struct {
    void *context;
    int (*send)(void *context, const unsigned char *data, unsigned int size);
} Transport;
```

补充接口约定：返回值表示什么？缓冲区在函数返回后是否仍会被使用？是否允许部分发送？是否可能阻塞？由谁处理重试？这些约定比只有一个函数指针更重要。

完成标准：协议编码模块通过两种实现发送同样的报文，编码代码不需要修改。

## 2. QP/C 示例：把异步流程写清楚

入口：

- `sources/qpc-examples/posix-win32/blinky/`：从 `main.c`、`blinky.c`、`app.h`、`bsp.c` 入手。
- `sources/qpc-examples/posix-win32/dpp/`：观察多个对象之间的事件协作。
- `sources/qpc-examples/posix-win32/defer/`：阅读延后处理事件的方式。
- `sources/qpc-examples/qutest/`：观察状态行为如何在主机或目标设备上验证。

记录一个事件从生成、投递到处理的路径，找出状态转移、进入/退出动作和硬件操作各自的位置。对照主机与板卡示例，观察 BSP 如何承接环境差异。

练习：为通信设备写一个连接与命令状态机。

| 当前状态 | 事件 | 下一状态 | 动作 |
| --- | --- | --- | --- |
| 未连接 | 请求连接 | 连接中 | 发出连接请求，设置超时 |
| 连接中 | 连接确认 | 就绪 | 清除连接超时 |
| 连接中 | 超时 | 故障 | 记录失败原因 |
| 就绪 | 发送命令 | 等待应答 | 发出命令，设置应答超时 |
| 等待应答 | 正确应答 | 就绪 | 更新业务状态 |
| 等待应答 | 超时 | 故障 | 记录失败原因 |
| 任意已连接状态 | 断开连接 | 未连接 | 清理待处理操作 |

表格是练习起点，应继续补齐重复请求、取消、失败恢复和迟到应答。业务状态在收到确认后变化；等待期间仍能处理其他事件。用请求编号或协议提供的标识区分当前请求与过期应答。

完成标准：通过输入事件序列验证成功、超时、断开和重复请求，可以用模拟设备代替真实硬件。

## 3. FreeRTOS-Kernel：区分模块、任务与平台

入口：`sources/FreeRTOS-Kernel/README.md`。

阅读顺序（以下路径相对于该项目目录）：

1. `include/task.h`、`include/queue.h`：先理解公开接口与阻塞语义。
2. `queue.c`：追踪一次发送、接收、阻塞与唤醒。
3. `tasks.c`、`list.c`：理解就绪、等待及超时组织。
4. `portable/` 中一个熟悉 CPU 的 `port.c`、`portmacro.h`：找出上下文切换和临界区机制。
5. `portable/MemMang/`：比较可替换的内存分配策略。
6. `examples/template_configuration/FreeRTOSConfig.h`：观察构建时配置如何影响内核能力。

研究重点：内核公共代码通过移植接口使用 CPU 能力，产品通过配置选择能力和内存策略。模块数量、任务数量与可替换接口数量分别由职责、时序和变化需要决定。

练习：设计一个传感器采集模块和一个处理模块，写清采样任务、处理任务、队列容量及满队列策略。区分可以丢弃的周期样本和必须可靠处理的控制命令；确认中断上下文使用的 API 与数据复制/所有权约定。

完成标准：能够解释为什么使用这些任务、哪里可能阻塞、队列满时如何处理，以及换 CPU 时主要替换哪些代码。

## 4. MCUboot：让升级核心可独立验证

入口：`sources/mcuboot/docs/design.md`。

再读 `boot/bootutil/`、`boot/zephyr/`、`sim/README.rst` 和 `sim/tests/`，路径相对于 `sources/mcuboot/`。

观察镜像处理核心、平台 Flash 接口和最终启动动作的边界。模拟器可以帮助研究升级中断、恢复和回退等行为。选择一个升级策略追踪，避免将不同策略的状态流程混在一起。

练习：画出“候选固件写入 → 校验 → 试运行 → 确认”的流程。列出每步之后掉电重启时的恢复动作，并区分 RAM 状态与持久化状态。用内存模拟 Flash 的擦除和写入限制，逐步注入失败。

完成标准：每个中断点都有可解释的恢复行为，升级状态不依赖下载 UI 或特定网络协议。

## 5. lwIP：理解通信分层与数据所有权

入口：`sources/lwip/README` 和 `doc/`，再看：

- `src/core/`：协议栈核心。
- `src/include/lwip/netif.h`、`src/core/netif.c`：网络接口与回调。
- `src/api/tcpip.c`：线程模式下的消息调度。
- `src/include/lwip/sys.h`：系统适配接口。
- `src/core/pbuf.c`：数据缓冲区和引用计数。

上述路径相对于 `sources/lwip/`。重点追踪一份数据从网卡接收、交给协议栈到释放的路径，记录每一步谁拥有缓冲区、由哪个上下文执行，以及能否阻塞。区分裸机和 RTOS 模式，按所选模式理解接口限制。

练习：为自定义通信协议设计接收缓冲区约定。明确由谁分配、何时复制、谁释放、队列满时如何处置；先用容易验证的方案实现，再衡量是否需要减少复制。

完成标准：在连续接收、超时、断开和处理拥塞时，数据不会因所有权不清而被提前释放或遗失。

## 专项 A. Zephyr 示例应用：隔离产品与平台配置

入口：`sources/zephyr-example-application/README.md`。

再看 `app/`、`boards/`、`drivers/`、`CMakeLists.txt` 和 `west.yml`，理解应用入口、板卡描述、驱动和依赖如何被装配。

练习：列出设备产品中三类独立变化：

- 板卡：引脚、总线、外设及硬件能力。
- 产品：功能集合与默认配置。
- 协议：帧格式、字段含义、版本差异。

为每类指定配置入口和负责模块。避免用同一个“产品型号”宏散布控制所有变化；同时保持当前实现需要的简单程度。

完成标准：新增板卡主要修改平台适配和构建选择；新增传感器主要修改设备实现；协议变化主要修改编解码器。

## 专项 B. InfiniTime：追踪完整产品中的协作

先读 `sources/InfiniTime/doc/code/Intro.md`，再读：

1. `src/main.cpp`：对象创建、依赖传递与启动入口。
2. `src/systemtask/SystemTask.cpp` 和 `Messages.h`：系统初始化、消息及工作循环。
3. `src/displayapp/DisplayApp.cpp`：页面运行、输入处理与任务消息。
4. `src/components/battery/` 与 `src/displayapp/screens/WatchFaceDigital.cpp`：追踪一种数据到界面的链路。

上面路径均相对于 `sources/InfiniTime/`。

需要画出两种图：模块依赖图，以及运行时任务/消息图。模块可以有独立职责，但不必各自拥有线程。观察页面持有哪些控制器引用，并判断这种依赖是否适合自己的产品。

练习：为传感器设备设计业务状态与展示状态。

```text
传感器输入 → 数据校验 → 设备业务状态 → 只读快照 → 串口报告或显示模型
```

设备业务状态保存测量值、有效性和告警；展示模块负责单位转换、文字格式或图形表现。输入操作形成命令，由业务模块验证并执行。

完成标准：串口报告与显示界面读取同一份设备快照；更换展示方式不会改变采样值或告警规则。

## 专项 C. LVGL：研究 UI 的边界

入口：`sources/lvgl/README.md`，再从 `examples/` 与 `demos/` 选择一个小例子。

观察显示与输入适配、控件事件、对象创建/删除及更新方式。阅读时记录页面退出后哪些资源需要释放，哪个执行上下文允许操作 UI。

练习：设计页面的 `enter`、`update`、`leave` 约定。`update` 接收显示模型，页面事件输出明确命令。将设备 I/O 安排在允许阻塞的执行上下文，完成后再通知界面。

完成标准：反复进入/退出页面不会留下重复定时器或失效回调；设备等待不会使界面停止响应。

## 最后做一个小项目

实现一个小型传感器采集与告警程序，可以先在电脑上模拟输入，再移植到开发板：

1. 定义传感器接口，提供模拟输入和板卡输入实现。
2. 采集模块输出类型明确的数据，核心处理不引用厂商驱动头文件。
3. 一个模块维护设备状态与告警，其他模块读取一致快照。
4. 用串口、文件记录或界面输出结果，明确阻塞和缓冲策略。
5. 使用固定输入验证超时、告警、防抖与故障恢复。

成果应包含接口头文件、状态/依赖图、输入样例，以及“增加平台、传感器或输出方式时修改哪些文件”的说明。

评估架构时看实际修改范围、故障隔离和验证能力；目录数量或抽象层数量不能单独证明高内聚、低耦合。
